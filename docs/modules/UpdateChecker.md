# UpdateChecker (`Managers/UpdateChecker.cs` + `build/update.ps1`)

Notices that a newer release exists on `github.com/VagnerVit/NGUAdvisor` and installs it on the next
launch. Three pieces, deliberately split across the process boundary:

| Piece | Runs | Does |
|---|---|---|
| `Managers/UpdateChecker.cs` | inside the game | spawns the script every 6 h, reads `update.state`, exposes `Available` / `LatestVersion` |
| `injector\update.ps1` (source: `build/update.ps1`) | Windows PowerShell | the only thing that touches the network; `-Check` reports, `-Apply` installs |
| `Run NGU Advisor.bat` (generated by `package-release.sh`) | before injection | writes `install.txt`, runs `-Apply`, then injects |

## Why the network lives outside the game

The advisor runs in NGU Idle's Unity 2019.4 Mono domain, whose TLS stack and root certificate store
cannot be relied on to complete a handshake with `api.github.com`. Rather than shipping a TLS
workaround into the game process, **no HTTPS client exists there at all**: the advisor starts
`powershell.exe`, which has the host's real trust store, and reads the answer from a file.

That is the same handshake shape as `Loader.UnloadRequestPath()` and `StateExport.RequestPath` — one
side drops a file, the other polls it — and it is the reason `Process.Start` is safe from the Unity
thread: it does not block and touches no Unity object.

## The version comes from the advisor, never from the DLL

`Main.Version` is the only trustworthy SemVer in the build:

- `Properties/AssemblyInfo.cs` still declares `1.2.2` — the hand-maintained attributes drifted years
  of releases ago, so `FileVersionInfo` on the DLL reports a wrong answer confidently.
- the assembly NAME is `NGUAdvisor.r<yyMMddHHmmss>` (Mono byte-load dedup, `Main.BuildTag`), a build
  stamp and not a version.

So `-Check` is passed `-CurrentVersion` by the running advisor and records it as `installed=` in
`update.state`; `-Apply`, which has no advisor to ask, reads that line back, falling back to the
`version=` line in `injected.txt` (added to `Loader.WriteMarker` for exactly this). **The game's own
version is never read** — NGU Idle is done shipping updates and nothing here is gated on it.

## `install.txt` — how the advisor finds its own folder

`smi.exe` loads the assembly from BYTES, so `Assembly.Location` is empty and the advisor genuinely
cannot tell which folder it came from. The launcher writes `%~dp0` into
`%LocalLow%\NGUAdvisor\install.txt` before injecting, and that is the only route from the game
process back to `injector\update.ps1`. No file (someone injected by hand, normal on a dev machine)
means no update checks — logged once to `debug.log`, never an error.

## `update.state`

`key=value`, one writer (the script), same shape as `injected.txt` so neither side needs a parser:

```
available=1
checkedUtc=2026-09-17T15:29:02.4807564Z
installed=1.6.5
latest=1.6.6
url=https://github.com/VagnerVit/NGUAdvisor/releases/download/v1.6.6/dist_1.6.6.zip
appliedUtc=...
```

The advisor polls its mtime inside `Main.Update()`'s existing once-a-second budget (NOT
`AutomationRoutine`, which returns early while the advisor is paused — a paused advisor should still
notice a release) and announces a new version in the rail footer, where the running version already
is.

## Rules the script obeys

- **Always `exit 0`.** An update problem must never be the reason the game does not get its advisor.
  Every failure logs to `logs\update.log` and leaves the existing DLL alone.
- **Back up before replacing, restore on throw.** A half-written DLL is an instant crash on inject.
- **6-hour throttle**, matched on both sides. The unauthenticated GitHub API allows 60 requests/hour
  per IP and an idle game is left running for days.
- **Only `NGUAdvisor.dll` and `update.ps1` are replaced.** `smi.exe` and `SharpMonoInjector.dll` are
  third-party tools that ship only to make the zip runnable, and `sampleprofiles\` may have been
  edited in place.
- **The release zip nests everything under `NGUAdvisor-<version>\`** (`package-release.sh` zips the
  stage FOLDER), so the DLL is located by recursive search rather than by an assumed path.
- **`Run NGU Advisor.bat` is never refreshed by an update.** `cmd.exe` reads a batch file line by
  line as it executes and the script is running FROM that file; overwriting it mid-run jumps cmd into
  garbage. A launcher change needs a manual re-download of the zip.

## Not done, on purpose

Applying an update to a RUNNING game. It is mechanically possible — drop `unload.request`, wait for
it to vanish (the ack), re-inject, and the new build's timestamped assembly name defeats Mono's
dedup — but `Loader.cs` states that this project has no hot-reload, and the two crashes documented in
Main.md came from exactly this neighbourhood. The update lands on the DLL that the next launch
injects, and the footer says so.
